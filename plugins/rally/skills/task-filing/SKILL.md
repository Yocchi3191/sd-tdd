# Task Filing

決定した内容をどこに・どのように記録するかを決める。起票されたタスクが、後から自分で読み返しても十分な文脈を持つ状態にする。

デフォルトのトラッカー: `gh` CLI経由のGitHub issue。

## 操作: 現在の本文を取得する

```bash
gh issue view <N> --json body -q .body
```

生の本文テキストをそのまま呼び出し元に返す。パースは呼び出し元が行う。

## 操作: 新規タスクを起票する

1. `task-template.md`（このskillのディレクトリ内）を読み、埋めていく:
   - **背景・課題** と **完了条件** は必須 — この2つの見出しは常に含める。
   - **やること・要件** の書き方は自由。**REQ台帳は必須ではない。** 台帳があれば転記し、無ければ箇条書きのやることリストでよい。まだ何も決まっていなければ空欄のまま起票してよい。台帳が無いこと自体はエラーではない。
   - REQ-N行を渡された場合は、**そのまま転記する** — 言い換え・要約・番号の振り直しは行わない。テンプレートのプレースホルダ行は完全に置き換える。
   - **決定事項**、**設計・実装方針**、**注意点・既知のトレードオフ** は任意 — 実際に関係がある場合のみ含める。空の見出しを残さないこと。
   - `rally:design` から引き渡された場合、**決定事項** には「決定内容 / 検討した代替案 / 却下理由」の3点を含める。
2. タスクを作成する:

```bash
gh issue create --title "<task title>" --body "$(cat <<'EOF'
<filled-in template>
EOF
)"
```

3. 呼び出し元へ報告する: 「issue #<N>として起票しました。」

## 操作: 既存タスクへ追記する

1. 現在の本文を取得する（上記参照）。
2. 新しい要件行を **やること・要件** セクションの末尾に追記する。既存の行を削除・言い換えしてはならない。REQ台帳形式の場合は`REQ-<max+1>:`から続ける。
3. 呼び出し元から任意セクション（背景・課題、完了条件、決定事項、設計・実装方針、注意点・既知のトレードオフ）への更新が渡された場合はそれも反映する — それ以外の本文はそのままにしておく。
4. タスクを更新する:

```bash
gh issue edit <N> --body "$(cat <<'EOF'
<updated full body>
EOF
)"
```

5. 呼び出し元へ報告する: 「issue #<N>を更新しました。」

## 制約: 既存のREQ行は書き換えない

REQ台帳を使っている場合、起票済みの`REQ-<id>:`行のテキストを編集しない。誤りだと判明したら、その行に`[superseded by REQ-<新id>]`を追記した上で、新しい行を末尾に追加する。

台帳を「今どうなっているか」だけでなく「どう変わったか」も読める状態に保つため。判断が変わった経緯こそ後から効く。
